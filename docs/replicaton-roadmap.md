Now the replication roadmap. Having read the new primitives' contracts, here's the shape of what's built and what's missing: EntryLog gives you the durable Raft log (sync() as the ack point, truncateFrom for the conflict rule, getBatch for AppendEntries batches), SnapshotStore gives crash-safe snapshot adoption, and bplustree/rtree/textlog now persist an appliedIndex atomically with every commit. The gap is that nothing in nisaba's db layer speaks any of this yet — wasm/src/db.c has zero applied-index awareness. The steps, in dependency order:

1. ✅ DONE — Thread appliedIndex through the db layer. Implemented as dc_applied_index/dc_set_applied_index (wasm/src/db.c, contract in wasm/include/db.h), surfaced as Collection.appliedIndex()/setAppliedIndex() and proxied through the coordinator. The design came out simpler than first sketched: because the collection's cross-file commit journal (DCTJ, dc_collection_recover) already rewinds every file to one consistent commit on crash recovery, per-file replay guards are unnecessary — one collection-level index suffices. setAppliedIndex stages the entry's index onto the primary tree and every attached structure (validated against all of them before staging any, so a refusal never leaves partial staging); each file's next commit persists it atomically with the mutation. appliedIndex() reads the primary tree — the authority, since every document mutation commits it — while untouched index files lag safely and catch up on their next commit (staged values are sticky). The apply loop's contract: guard each entry with `entry.index > appliedIndex()`, stage, apply; resume replay from appliedIndex() + 1. Tested in test/db.applied-index.test.js, including an interrupted-apply/full-replay equivalence check and an EntryLog write-ahead recovery integration (the step-2 loop in miniature).

2. Single-node WAL — Raft minus networking. Define the command format (binjson-encoded op descriptors) and rewire the write path: driver call → build command → EntryLog.append + sync() → apply via dcw_* with the applied index staged → reply. The critical design rule: all nondeterminism resolves at proposal time, so the same command bytes replay identically on any replica. Nisaba is already well positioned — _id generation and textlog timestamps deliberately live in JS and travel as parameters (default_id) — but audit db_update.c for any C-side clock/random use before freezing the format. Recovery becomes: open the log (torn-tail truncation is built in), replay from each collection's appliedIndex() + 1 forward. Ship and test this alone first — it's a durability upgrade in its own right, and it forces every hard correctness question before networking exists.

3. Snapshot + log compaction loop. Size-triggered: compact each collection's files into a SnapshotStore generation (bpt_compact works from an MVCC snapshot, so writes continue), commit the manifest at (lastIncludedIndex, lastIncludedTerm), compact the EntryLog through that boundary into the paired log file, prune. This bounds log growth and is the InstallSnapshot artifact for step 5.

4. Decide the topology — the real product decision. Multi-tab is already solved (the coordinator's navigator.locks election guarantees a single leader locally; Raft there would be redundant). The genuine options: browser replicas syncing against the cloud service as leader (offline-first), full Raft among service nodes for a durable backend, or peer-to-peer between a user's devices. My recommendation regardless of choice: build the Raft node as a transport-agnostic module (AppendEntries/RequestVote/InstallSnapshot over a pluggable message interface) so an in-memory transport drives tests and WebSocket/service transport is a thin adapter. If the near-term goal is client↔server sync, you can even ship leader-follower replication (fixed leader, no elections) on the same log format first and add elections later.

5. The Raft core itself. The EntryLog API was clearly shaped for this: setHardState before answering any RPC (it enforces Raft's persist-before-reply rule), termAt for the consistency check, truncateFrom on conflict, append+sync before ack, setCommitIndex riding the next sync, NOOP entries on election, CONFIG entries for membership. Follower snapshot install streams into a SnapshotStore generation and validates against the leader's manifest CRCs before adoption.

6. Read semantics and change streams. Decide follower read policy (stale-ok vs. leader leases vs. readIndex). And change streams get a structural upgrade: db-plan.md:781 notes MongoDB's change streams tail the oplog and nisaba had "no analog" — the entry log is the analog now, giving resumable, gap-free streams.

7. Testing, throughout. Deterministic simulation: in-memory transport with drop/delay/partition injection, plus crash-point tests that kill between append/sync/apply at every boundary (MemoryHandle makes that cheap, and the submodule's entrylog.durability-wasm.test.js is the model to copy).
