Now the replication roadmap. Having read the new primitives' contracts, here's the shape of what's built and what's missing: EntryLog gives you the durable Raft log (sync() as the ack point, truncateFrom for the conflict rule, getBatch for AppendEntries batches), SnapshotStore gives crash-safe snapshot adoption, and bplustree/rtree/textlog now persist an appliedIndex atomically with every commit. The gap is that nothing in nisaba's db layer speaks any of this yet — wasm/src/db.c has zero applied-index awareness. The steps, in dependency order:

1. ✅ DONE — Thread appliedIndex through the db layer. Implemented as dc_applied_index/dc_set_applied_index (wasm/src/db.c, contract in wasm/include/db.h), surfaced as Collection.appliedIndex()/setAppliedIndex() and proxied through the coordinator. The design came out simpler than first sketched: because the collection's cross-file commit journal (DCTJ, dc_collection_recover) already rewinds every file to one consistent commit on crash recovery, per-file replay guards are unnecessary — one collection-level index suffices. setAppliedIndex stages the entry's index onto the primary tree and every attached structure (validated against all of them before staging any, so a refusal never leaves partial staging); each file's next commit persists it atomically with the mutation. appliedIndex() reads the primary tree — the authority, since every document mutation commits it — while untouched index files lag safely and catch up on their next commit (staged values are sticky). The apply loop's contract: guard each entry with `entry.index > appliedIndex()`, stage, apply; resume replay from appliedIndex() + 1. Tested in test/db.applied-index.test.js, including an interrupted-apply/full-replay equivalence check and an EntryLog write-ahead recovery integration (the step-2 loop in miniature).

2. ✅ DONE — Single-node WAL — Raft minus networking. Implemented as src/db-wal.js (`nisaba/wal`, connectWal(provider)): WalDb/WalCollection mirror the driver surface; every write becomes a binjson-encoded command appended to a shared EntryLog (`__wal__.bj`) and synced durable BEFORE it applies; recovery replays the committed suffix each collection hasn't applied. All nondeterminism resolves at proposal time, and since the C pushdown the resolving is C's: wasm/include/db_wal.h owns the command grammar and the planner (dc_wal_plan_build) that produces it. The invariant it holds is that **every logged document command names exactly one _id**, so apply never runs a query. _ids are assigned before logging; $currentDate resolves to concrete Dates (the determinism audit found it — resolveCurrentDate is now exported for this); matched writes resolve to their target _id (no-match non-upsert writes aren't logged at all); an upsert that found no match is resolved the whole way — the planner builds the document it would have inserted and logs a plain insert, retiring the `uu`/`ru` commands that used to carry a filter into the log for apply to re-evaluate, and with them the second full query every upsert used to cost; pruneExpired's TTL cutoffs become concrete Dates in ordinary logged deletes. The planner also returns the matched document, so the findOne (or projected find) that used to precede every logged write is gone — resolving the target had already read it. Multi-document writes decompose into per-document entries (the engine commits per document — dc_update_many — so one entry must equal one commit) with one sync() per batch (group commit), like MongoDB's oplog. Writes serialize through one chain so log order is apply order; a freshly-logged command whose apply fails is truncated back out of the log (ordered batches retract their never-applied suffix), and recovery tolerates unordered-batch residue by re-running it into the same deterministic error. Not logged: reads, index DDL (safe — see the file's header for why backfill can't double-count), compact; dropCollection is refused until step 3's log compaction provides a barrier. Tested in test/db.wal.test.js: driver-shape equivalence, what-gets-logged accounting, retraction, forged crash-window recovery, upsert-logged-as-insert replay, refusal of an entry naming an unknown op, the no-filter-in-the-log invariant across every write shape, mid-batch resume, double-reopen idempotence, concurrent-write serialization, read-your-writes, TTL pruning.

3. ✅ DONE — Snapshot + log compaction. WalDb.snapshot() (src/db-wal.js): quiesced under the write chain, it streams the catalog and every collection structure into an immutable SnapshotStore generation via each wrapper's compact() (reads from the live trees; the manifest's `config.live` maps each role back to its live file name), commits the manifest at the log tail (every logged entry is applied at a quiesced moment, so lastIncludedIndex/Term = lastIndex/lastTerm), then compacts the EntryLog through the boundary into the store's paired `-log-<gen>` file, adopts it, prunes predecessors, and deletes the legacy `__wal__.bj`. connectWal() adopts the newest valid generation on open (SnapshotStore sweeps crashed/superseded ones) and the newest log that opens — generation logs newest-first, legacy file last — falling back past a torn newest log to its predecessor, which is only ever pruned after a successor is durable. restoreLatestSnapshot() is the local half of an InstallSnapshot: wipe the live db files (including stale journals, which could otherwise rewind restored files), CRC-verified stream-copy each generation file to its live name, reopen; recovery replays any log suffix beyond the boundary. dropCollection is now legal: the (unlogged) drop is followed by a barrier snapshot, so no pre-drop entry survives to resurrect the collection. SnapshotStore plugs into any StorageProvider with listFiles() via a small directory-handle adapter; without listFiles(), snapshot/dropCollection are refused. Index DDL and compact serialize against snapshots (they change the file set mid-generation otherwise). Snapshotting stays host-driven, matching compact()/pruneExpired()'s convention — trigger on `db.log.fileLen` growth. Tested in test/db.wal-snapshot.test.js: log bounding + continued writes, generation completeness/CRC verify/supersession, snapshot+suffix == full-history equivalence, boundary-exact restore, all index kinds surviving restore with their appliedIndex, drop-barrier no-resurrection, drop-and-recreate replay, torn-paired-log fallback, and unapplied-suffix replay on the generation log.

4. ✅ DECIDED — Topology: server-side clustering. Full Raft among service nodes to create a durable, failover-capable cloud; browsers stay plain remote clients (nisaba/remote) for now, becoming cache/read replicas later as non-voting followers (snapshot install + log-suffix streaming + change streams tailing the log — all machinery from steps 2/3). Offline WRITES are explicitly out of scope and will never fit Raft: when wanted, they arrive as a queued-replay layer with an app-visible conflict policy on top — do not promise apps transparent offline writes. The recorded decisions:
   - Full Raft with pre-vote from day one (any node can lead); leader stickiness to avoid disruptive re-elections.
   - One Raft group per tenant database (one WalDb = one log = one group), matching the tenant-worker model. The service layer must coalesce heartbeats per node-pair and quiesce idle groups — with mostly-idle tenants this is the design, not an optimization.
   - Reads: DECIDED (docs/steps/read-semantics-and-change-streams.md, part one). Every read is linearizable, only the LEADER serves one, and it serves it behind a real ReadIndex barrier -- a fresh heartbeat round to a quorum, not a lease, because nothing in this codebase assumes bounded clock skew and a lease would be the first. A follower refuses a read exactly as it refuses a write (-63 with the leader's id and address); ping is the one exemption. A partitioned leader refuses rather than answering from what it holds, which closes a hole that had shipped: reads were served by ANY member with no check at all, and hasQuorumContact -- written for precisely this -- was never called by the server. Stale follower reads are NOT the later opt-in the earlier note imagined: under a linearizable rule a follower read still costs the leader a round trip, so it distributes query WORK and does not scale reads. Scaling comes from an asynchronous replica tier outside consensus, deferred to its own brief and explicitly non-linearizable.
   - DDL (createIndex/dropIndex/dropCollection) must become logged commands under replication — the single-node "unlogged DDL is safe" argument dies with the first follower. ✅ DONE in both hosts. JS: 5c, as commands with idempotent apply. C: the server plans DDL into a command and performs it through `dbs_apply` (`db_session.h`), the new session-level applier — `dc_wal_apply` drives the four document ops and refuses the DDL three, because those make and unmake FILES, which belongs to whoever owns the namespace. So a C process can now apply a committed entry of ANY kind; it needed a JavaScript host for exactly three opcodes before. The C server writes a log now: with `--raft` the command is proposed and applied only once it has committed, which is the change that was always going to be made in one place (`server/replica.c`); without it, the command is still built and applied in one breath. `createCollection` stays commandless in both hosts: an insert makes a collection implicitly and that insert is logged, so only a collection named and never written to fails to travel. `DC_ERR_INDEX_EXISTS`/`DC_ERR_NO_INDEX` joined `dc_is_deterministic` (a replayed DDL command converging is an answer, not a halt); `DC_ERR_NO_COLLECTION` deliberately did not.
   - Transport: request/response interface (call(peerId, msg) → reply, binjson-framed); WebSocket adapter in the service, in-memory adapter for the deterministic simulator. The Raft node never owns a socket.
   - Node identity: stable small-integer ids (votedFor persists as a number); cluster membership static config first, CONFIG entries later.
   - Audit item before production: the server storage provider's flush path must be a real fsync — Raft safety depends on sync-before-ack reaching disk.
   - Cost accepted: quorum write latency (batching mitigates throughput, not latency) and 3x storage/compute per tenant.

5. ⏳ IN PROGRESS — The Raft core itself.
   - ✅ 5a: core + simulator. src/raft.js (`nisaba/raft`): a transport-agnostic RaftNode replicating one EntryLog per group. Elections with pre-vote (persists nothing, bumps no term — an isolated node rejoins without dethroning a live leader) and leader stickiness; NOOP on winning (§5.4.2 term boundary); AppendEntries with the termAt consistency check, truncateFrom conflict repair, hintIndex backtracking, and sync-before-ack; commit advancement by quorum match counting current-term entries only; an ordered apply pump feeding NORMAL entries to a state machine gated by its appliedIndex. Deterministic by construction — no clock, no Math.random: time arrives via tick(now), jitter via injected rng; the transport is one function (call(peerId, msg) → reply) with handleMessage as the receiving half. All EntryLog ops are synchronous, so every RPC handler runs without interleaving — the async seams are only the network and the state machine. test/raft-harness.js is the step-7 simulator (virtual clock, seeded rng, in-memory network with delays/partitions/unreachable failures, MemoryHandle-backed logs); test/raft.test.js covers election uniqueness/stability, single-node degenerate clusters, NotLeaderError hints, replication convergence, 40-deep concurrent bursts, minority-leader phantom-write discard, pre-vote term hygiene, crash-stop restart from persisted state, leader loss, and a multi-seed chaos test (random partition/heal cycles under continuous load: convergence + no acknowledged write lost).
   - ✅ 5b: InstallSnapshot streaming. RaftNode gains a pluggable `snapshotter` ({ latest, openFile } leader-side; { beginInstall → writeChunk/commit/abort } follower-side) and a `rebaseLog` hook (EntryLog cannot rebase in place: after commit the node closes its log, gets a fresh one based at the boundary, and re-persists hard state onto it). The leader streams the manifest with the first chunk then every file chunk-by-chunk over the same request/response transport, each chunk awaited (stale term aborts; success leaves the peer at the boundary and ordinary AppendEntries resumes). Follower commit + log swap serialize through the apply chain; a failed commit (checksum mismatch) adopts nothing and asks the leader to restart; a superseding manifest or a real election aborts a half-staged install. Fixed a design bug the tests caught: a blank replacement node reusing an id regresses below its old matchIndex — the leader now believes the follower's hint and drops matchIndex with it, so a disk-loss replica stops counting toward quorums and nextIndex can fall back to the install path. Also learned (and now documented in the tests): a delayed pre-compaction AppendEntries in the network can legitimately heal a lagging follower without an install — the simulator drains in-flight messages when the test needs to force the install path. Tests: multi-chunk lagging-follower catch-up, blank-disk node replacement then normal following, stale-term refusal, and no-snapshotter parking with host-intervention recovery. The 5c WalDb adapter maps this contract onto SnapshotStore (latest/openFile exist verbatim; beginInstall ≈ store.begin + restoreLatestSnapshot).
   - ✅ 5c: WalDb integration — src/db-replicated.js (`nisaba/replicated`, connectReplicated). The WAL's commit engine became pluggable: WalCollection is unchanged (all proposal-time determinism carries over verbatim), and WalDb._commit — local append/sync/apply/retract — is overridden by ReplicatedDb with the Raft path: propose each command, await quorum commit + local apply, collect the apply's result from the state machine (the ack point moved; retraction is gone — a committed command that fails deterministically is a result every replica computes, not log garbage; NotLeaderError aborts the whole operation as a routing condition). DbStateMachine runs WalDb._applyCommand — the same code as single-node live writes and crash replay — swallowing deterministic command errors so the apply pump never mistakes an application failure for divergence; appliedIndex() = max over collections (apply is strictly ordered, so the max is the applied prefix). DDL is now logged in BOTH modes (createIndex/dropIndex/dropCollection as commands with idempotent un-guarded apply; the single-node drop-barrier snapshot is gone — the drop entry itself re-drops after any transient replay resurrection). The SnapshotStore maps onto the 5b snapshotter contract: latest()/openFile() serve installs from the adopted generation; beginInstall stages a new generation via store.begin() with incremental CRC validation against the leader's manifest before commit, then adopts it live — close the inner Db, restoreFromStore, reconnect, repoint cached WalCollections — behind a read gate so async reads can't touch freed WASM contexts mid-swap (sync-shaped cursors across an install window remain a documented 5d hazard). Local snapshot() on a live member runs inside RaftNode.runExclusive (new: quiesces handlers/ticks/proposes and drains applies) with the boundary at lastApplied, never baking in an uncommitted suffix. Replicated open does NO blanket recovery replay — the RaftNode applies exactly the committed prefix. Tested in test/db.replicated.test.js: replica convergence, leader-only writes with retry hints, cross-replica determinism (_ids/upsert ids/$currentDate timestamps byte-equal), replicated DDL, deterministic-failure surfacing with intact logs, leader failover, restart catch-up from own disk, and blank-member bootstrap by chunked snapshot install through the real SnapshotStore.
   - ✅ 5d (nisaba-db side): the generic clustering infrastructure. What remains beyond this is nisaba-web composition (tenant→group provisioning, gateway leader-routing, auth/TLS, ops) — the boundary recorded below.
     · Membership: the member set travels as CONFIG entries (encode({members}), full-set replacement), proposed one at a time via RaftNode.changeMembership(), adopted at APPLY (etcd convention — truncation-proof, safe for serialized single-server changes); recovered at restart by the latest-in-log rule (the advisory commit index lags, and a volatile state machine's appliedIndex can sit past CONFIG entries); carried in the install manifest for bootstrapped members. A node applying its own removal steps down and stops campaigning. Two pre-vote hardenings fell out of the tests: a healthy LEADER always refuses pre-votes (the classic disruption is a removed-but-unaware member with an up-to-date log pre-voting at the working leader), alongside the existing follower stickiness.
     · RaftGroupHost (`nisaba/raft-host`): one process seat across many groups — per-group transport shims over one envelope transport ({group, msg}), one tick loop, and idle-group quiescence done properly: the host only idles LEADERS, and RaftNode.quiesce() on a leader first parks every follower via a flagged final heartbeat (follower election timeouts are shorter than any sane idle threshold; host-side idling of followers misreads leader silence as leader death and churns elections — the simulator caught exactly that). A quiesced group is zero bytes on the wire; any envelope or touch() wakes it; a leader that dies quiesced is replaced lazily on next use. Heartbeat coalescing across groups is left as a transport concern — quiescence does the heavy lifting.
     · TcpRaftTransport (`nisaba/raft-tcp`): the zero-dependency reference node-to-node transport — node:net, length-prefixed binjson frames (entry payloads and snapshot chunks ride as native binary), one lazily-dialed socket per peer carrying every group's envelopes, redial-on-next-call, timeouts as the only retry policy (Raft's heartbeats do the rest). Two lifecycle bugs found by tests: server.close() waiting forever on live inbound sockets, and a dead socket's late 'close' tearing down the healthy replacement connection (drop is now by connection identity). Verified by a REAL 3-node KV cluster over localhost sockets with real timers.
     · fsync audit: the Node provider's flush() was already a true fsyncSync (contract documented in-file); one real gap fixed — file CREATION now fsyncs the parent directory (POSIX can lose the directory entry of a fsynced file on crash, which would silently drop a fresh WAL log or snapshot generation file out of the crash-safety reasoning).
     · Join-via-any-node + addresses-in-the-log (docs/clustering.md): CONFIG entries carry member RECORDS ({id, host, port, ...} — full-set replacement, id-only inputs inherit known records so addresses can't be erased); every adoption path (bootstrap, apply, restart scan, snapshot install) funnels through one method firing the onConfig hook, and RaftGroupHost.addGroup chains it to transport.setPeer — the peer table can never drift from the log BY CONSTRUCTION (add/update only; pruning is host policy since transports are shared across groups). 'join'/'leave' ride the ordinary transport to any member: a follower's refusal carries the leader's id AND address, the leader upserts/removes via changeMembership and replies with the adopted records at commit; retries are idempotent. Both reference transports gained callAddress(addr, envelope) (a joiner knows addresses, not ids) and joinGroup/leaveGroup drive the seed loop — spinning up a node is: start transport, joinGroup with one seed address, connectReplicated with the returned records, addGroup. Restarts need no join (the log restores ids and addresses even with empty bootstrap peers); the bootstrap node lists itself WITH its address. Extra record fields ride untouched.
     · Join/leave in the NATIVE server (docs/db-server.md): `nisaba-server --raft ID --raft-port N --join HOST:PORT` is the same flow with flags instead of an API — `server/join.c` runs the seed loop over `peers_call` (a one-shot to a bare ADDRESS, because a joiner has seeds and not ids), following the redirect a follower gives and stopping on a validation refusal that will never heal. The node had answered join/leave since before the server was a replica; what was missing was the caller and ONE real gap — a join's reply is DEFERRED until its CONFIG entry applies, so the conversation has to outlive the rn_handle call. server/replica.c keeps a bounded correlation table for it, keyed on ids it MINTS (two joiners both send id 0, so the sender's would collide). Argv became a bootstrap: the last CONFIG entry in the log wins at startup and at every apply, and the peer transport's addresses follow the adopted set (peers_set/peers_remove) rather than being a second copy. joinGroup(transport, null, …) sends the message bare, which is how a Node member joins a native cluster — the {group,msg} envelope is RaftGroupHost's multiplexing, and a native member hosts one group.
     · Learners (docs/clustering.md): a NEW member always joins as voting:false — join forces it, so adding capacity can never thin the failure margin. Learners receive full replication (AppendEntries + snapshot installs) but carry no quorum weight, never campaign (inert election timers), and refuse votes even from stale-config candidates. The leader auto-promotes on replication success once a learner's match index covers the commit index — proposing the record with explicit voting:true (explicit, not flag-dropped: changeMembership's id-merge would otherwise re-inherit the old flag); a busy CONFIG moment retries on the next success. Re-joins keep existing voting status; id-only changeMembership can't accidentally promote; a demoted leader steps down at apply. node.voters vs node.members exposes the split. Tested: offline-learner quorum exclusion (voter dies, commits still flow where a counted 4th would hang), no-campaign/no-vote guards, catch-up → auto-promotion → post-promotion quorum weight, id-merge flag preservation, and promotion asserted in the real-TCP grow-by-joining flow.
     · Observability (`nisaba/raft-monitor`, docs/clustering.md): RaftNode gained onEvent (state-TRANSITION events only — elections/role changes/config/promotions/installs/edge-triggered peer reachability/quiesce/conflict truncations/the critical apply-halt — never per-heartbeat noise) and status() (one JSON-able snapshot incl. the leader's per-peer match/lag/reachable view); RaftGroupHost aggregates events across groups (tagged {group}) and snapshots all of them; ReplicatedDb.status() adds db facts. RaftMonitor is a standalone read-only debug server (separate from the cluster transport, loopback by default): GET /status = one-off snapshot, GET /events = SSE stream with snapshot-first contract (event zero is full status, then live events) — curl -N or browser EventSource.
     · HttpRaftTransport (`nisaba/raft-http`): the infrastructure-friendly sibling of raft-tcp — Raft is purely request/response and leader-initiated, so plain HTTP fits the transport contract with no push channel: one POST per call, binjson bodies as application/octet-stream (binary stays native). Same contract, pick per deployment: HTTP buys TLS/auth-header/firewall/observability compatibility at ~150–200 bytes of header overhead per call (mostly moot under quiescence) and a head-of-line risk on the keep-alive pool (bounded by maxSockets; Raft tolerates the reordering). Keep-alive is load-bearing — an explicit pooled Agent, with the server's keepAliveTimeout raised past the client's reuse window so quiesced groups don't churn ECONNRESETs on wake. Peers must be DIRECT addresses: a load balancer breaks node identity. Verified by the same suite shape as raft-tcp, including a real 3-node cluster over localhost HTTP.
